Your job is to red-team an agent using decomposition and recomposition. Find cases where its answer to a compound question conflicts with its independently produced answers to the component questions, or where those component answers cannot support its proposed combined solution. You do not need to specify correct outputs upfront: specify the relationships that must hold between answers instead.

Unlike paraphrase fuzzing, a compound question and an atomic question do not ask for the same amount of information. Unlike counter-fuzz, design the atomic questions before seeing the compound answer; do not let the target's first response determine what gets tested.

Before generating sets, inspect the target's available code and documentation to identify meaningful behavior surfaces. Prefer realistic technical tasks involving interacting requirements, state scope, persistence, execution semantics, configuration, or error handling. Use authoritative sources to understand the concepts, without inserting the correct conclusions into the questions.

For each set:

1. Write a shared scenario that fixes the product, language, version assumptions, environment, and relevant constraints. Prefer a local library scenario when deployment infrastructure would change the answer.
2. Write one coherent compound question covering about three concrete subproblems and asking for a combined recommendation or execution explanation. Avoid unrelated grab bags.
3. Before asking the target anything, write one standalone atomic question per subproblem. Repeat all shared assumptions needed to answer it correctly. Narrow the requested scope, not the facts or constraints that could affect the answer.
4. Define comparison slots and relational expectations in advance. For each slot, identify the corresponding compound and atomic question IDs. Specify agreement on a proposition, configuration requirement, predicted result, or necessary consequence, not a reference answer. Preserve modality: a recommendation is not a requirement, and lack of a guarantee is not guaranteed failure.
5. Optionally prewrite a recomposed question that asks for a concrete combined solution to the same scenario. It must preserve the original assumptions and not add new behavior. This tests integration beyond separately answering the subproblems.
6. Send the compound, atomic, and optional recomposed questions as independent fresh target-agent runs. Do not include the other answers or refer to previous exchanges. Freeze the questions and expectations before execution. If the task is only to generate questions, stop here without calling the target.
7. Extract the relevant claims from the exact answers, preserving conditions, exceptions, and uncertainty. Recompose the atomic claims yourself into a constraint ledger: what would a combined solution have to satisfy if these claims were true? Do not invent missing claims or infer that independently possible features necessarily work together.
8. Compare each compound claim with its atomic counterpart, then check the compound and recomposed solutions against the ledger. Look for direct contradictions, properties assigned to the wrong component, recommendations that violate an asserted prerequisite, or integration that silently drops a constraint. Do not compare whole-answer similarity: a broader answer should contain more information.
9. Review candidate violations yourself. Omission alone, extra detail, different valid solutions, and compatible caveats are not contradictions. Mark ambiguous or missing comparison slots as inconclusive. Reject comparisons that changed assumptions, versions, or the strength of a claim. Account explicitly for interactions that explain why a component behaves differently in combination.
10. For correctness findings, establish the truth using authoritative documentation, source code, or a focused executable reproduction. Without reliable evidence, label a valid contradiction as an unverified inconsistency, not a confirmed incorrect answer. Agreement is not proof of correctness; all runs could share the same error.

Start with about three sets, each containing one compound question and three atomic questions, plus an optional recomposed question. Review distinct propositions rather than reporting several wordings of the same failure. Do not rerun a candidate to make it disappear; preserve the exact answers and trace IDs that exhibited it. One observation establishes occurrence, not frequency.

Save generated sets with stable set/question IDs, roles (compound, atomic, recomposed), full standalone questions, comparison slots, relational expectations, and source links. Do not include expected factual answers in the question-generation artifact. The independent questions can be exported to an `id,question` CSV and run with the existing `counter-fuzz ask` command; its ask step is reusable, but its two-response record format does not represent an entire decomposition set.

If executed, save the original responses with `set_id`, `question_id`, `role`, `question`, `answer`, and `trace_id`. Save reviewed comparisons separately with `set_id`, `comparison_slot`, the exact participating question IDs and trace IDs, quoted claims, `expected_relation`, `observed_violation`, `outcome`, `authoritative_evidence`, `correct_conclusion` when established, and `reasoning`. Keep confirmed correctness findings separate from unverified inconsistencies and inconclusive attempts.
